SSTVAE native app — interface review & redesign proposals

doc-id sstvae-ui-rev-2026-08-01 · reviewed at commit 8adeaf2 · target: native/gui/ (the Python GUI is frozen — bug fixes only, so every proposal here lands in the C++ app) · mockups are code-derived recreations; Qt6 is not installed on the review machine, so sstvae-gui-shot could not render real screenshots

§1Scope & method

Two code explorations mapped the entire native GUI (native/gui/, 8 widget pairs) and the frozen Python reference (sstvae/gui/ plus the rx/tx engines and rig controller), with every status-emission point and every user-visible text surface inventoried. Findings cite file:line against commit 8adeaf2.

The review covers the four requested items — crop UI for non-4:3 images, dual-pane TX/RX, persistent CAT/status output, a scrolling status log — and a comprehensive sweep beyond them (§8). Each major proposal has a current-state and proposed-state mockup and, where a real design choice is open, a decision picker in §10.

Everything here is UI-layer only: no on-air format, modem, or engine-contract changes. The engines already emit nearly all the information the proposals display — the single biggest gap is that the GUI drops it.

§2Executive summary

The app is functionally complete and the engine layer underneath is unusually well instrumented — but the presentation layer funnels everything through three one-line labels and ten modal dialogs. The result: safety-relevant errors are provably destroyed within a fraction of a second, a third of the state the engines publish is never displayed at all, and the operator cannot watch the band while composing a picture.

The one-sentence diagnosis The engines were built to be observable (rx::Progress even carries a polls counter specifically so "alive but hearing nothing" can be told from "wedged" — rx/engine.hpp:118-123) and the GUI throws that observability away at the last inch. Most of §6–§7 is wiring that already-queued signal traffic into surfaces that persist.

§4F1 — Croppable non-4:3 images

Current behaviour

images::fit() scale-to-covers 640×480 and centre-crops, always, silently (images.cpp:35-60; identical in sstvae/images.py:64-83). A 16:9 photo loses ~25% of its width; a portrait photo loses most of its height — typically the subject's head. There is no crop control, no warning, no "letterbox instead" option, and grep crop across both GUIs returns nothing. The only feedback is the cropped result itself, letterboxed inside the editor in a way that suggests nothing was cut.

Proposal: frame dialog on load, re-openable from the editor

When a chosen image isn't 4:3, open a modal frame dialog: the full original with a draggable, aspect-locked 4:3 window over it, dimmed outside; a zoom slider (zoom > cover allows tighter crops); an optional letterbox mode for when the whole frame matters more than filling it. The result feeds the existing fit path as a crop offset + scale — a parameter addition to images::fit, no format change. A 4:3 image skips the dialog entirely. An "Adjust framing…" button in the Picture group re-opens it (the original path is kept for the session).

  • The Picture group's label gains the honest caption: IMG_2437.jpg · 4000×3000, cropped to 4:3, and an Adjust framing… button.
  • Below-minimum images (< 320×240, currently upscaled without a word — images.hpp:25-26) get a one-line warning in the same dialog.
  • Open design choices — dialog vs. in-editor mode, and whether letterbox is offered — are Q2/Q3 in §10.

§5F2 — Dual-pane main window

Current behaviour

RX and TX are two tabs of a QTabWidget (main_window.cpp:32-36). Composing a picture means going blind: no waterfall, no decode progress, no incoming preview. The one cross-tab affordance is "Add last received image" on the TX side. Half-duplex interlock already exists (transmit suspends receive and rig polling — main_window.cpp:42-52) but its state is invisible from the Transmit tab.

Proposal: RX monitor and TX composer side by side, log dock below

Replace the tab widget with a horizontal splitter: a RX monitor pane (waterfall, picture, decode status, last-reception card) and the TX composer (editor, overlay tools, send bar). Below both, the status log dock (§7). The status bar gains a PTT lamp and keeps frequency/model/callsign chips (§6). At the default 1100×800 both panes are workable; the splitter lets either dominate, and each pane collapses to a strip for small screens (that behaviour is Q1 in §10).

Layout note: the "Selected item" property form stays, appearing below the overlay buttons when an item is selected (elided in the mockup for space). Nothing in the TX panel loses function; it narrows from 3:1-of-window to ~60% of it.

§6F3 — Status that persists: a severity model

Current behaviour

Every message in the app has equal weight and no lifetime guarantee. The inventory (full audit in §3 legends): TX errors are plain grey text overwritten by the next phase change (tx_panel.cpp:652, 637-639); on a failed send no terminal status is written at all (tx_panel.cpp:654-673); RX errors survive ≤ 500 ms (rx_panel.cpp:401); rig errors replace the frequency readout with deduplicated raw exception text (controller.cpp:86-88); the saved-file path lives 5 seconds (main_window.cpp:62); clipping is an unlatched colour (waterfall.cpp:251-256).

Proposal: three tiers, each with a rule

TierSurfaceLifetime ruleExamples
ErrorColoured sticky banner across the owning pane + log entryStays until dismissed (×) or the same subsystem succeeds. Never overwritten by routine state.PTT OFF FAILED · watchdog fired · autosave failed · audio device lost · config not writable
StateDedicated indicator, not shared textReflects current state, always visiblePTT lamp (red while keyed) · rig chip: frequency, greyed when polling paused, error-coloured with age ("CAT error · 45 s") on failure · latched CLIP badge on the level meter, click to clear · model chip with download progress
ProgressThe existing labels/bars, unchangedFree to overwrite each otherframe counts · "sending (32 s)" · refinement estimate

How errors surface (banner vs. status-label colouring vs. log-only) is Q6 in §10; everything in the State row is uncontroversial and carries no open design question.

§7F4 — Status log dock

Current behaviour

There is no logging of any kind in the GUI or core/ — no qDebug, no file, no ring buffer; the grep is empty outside the three CLI apps. Ten modal dialogs and every transient label vanish without record. When an operator asks "did it autosave? why did the rig drop? what happened while I was away?", the app has no answer.

Proposal: timestamped scrolling log fed by existing signals

A collapsible dock at the bottom of the main window (visible in §5's mockup): monospace, timestamped, severity-tagged lines with a source filter and a Copy button. No new plumbing is needed — these signals already exist and are already queued to the GUI thread:

SourceSignalLog line it becomes
rigAppState::rigStatus app_state.hpp:78connect / frequency change / CAT errors (now with timestamps, so dedup stops hiding repeats)
rxReceivePanel signals rx_panel.hpp:75-84sync acquired · reception complete (mode, SNR, frames, saved path) · errors
txTransmitPanel::stateChanged/errorOccurred/sendFinished tx_panel.hpp:84-89keying / sent / cancelled / failed · PTT failures · watchdog
appmodelLoaded, settings::LoadResult::notes settings.hpp:194-198model ready/failed · config-file validation notes, currently discarded wholesale app_state.cpp:29
optoptimizerProgressed + SpeculativeStatus.stop speculative.hpp:66-75"refined +1.2 dB est. (plateau, 41 steps, 12.3 s)" — stop reason is currently dropped, so plateau and timeout look identical tx_panel.cpp:198-223

Every QMessageBox the app shows also writes its text to the log before opening, so dismissed dialogs stop being unrecoverable. Whether the log also goes to a file on disk (invaluable for the PTT-timing shakedown against a physical radio that's still on the project's remaining list) is Q5; dock placement/behaviour is Q4.

§10Decisions & feedback

Settled 2026-08-01 — all seven questions answered (recorded on SSTVAE-9c8) Q1 split-full · Q2 dialog-on-load · Q3 no (crop only — the frame dialog loses its letterbox toggle) · Q4 bottom-dock · Q5 rotating-file · Q6 banner · Q7 observability-first. Every pick matched the recommendation.

Style amendment: keep the look traditional and Qt-native — no styled chips, pills or badge colouring; plain Qt widgets with palette colours at most. The mockups above are illustrative of information placement, not of visual style; the implementation follows the codebase's existing QPalette-only rule. Functionality, not style enhancements.
